# reward-smoothness — 액션 저크 페널티  `L2 · BUILD`

## 목표

정책이 관절을 **덜컥거리며** 움직이지 않도록 벌하는 항을 만든다.

```
jerk = a_t - 2*a_{t-1} + a_{t-2}          (2차 유한차분)
reward = sum_j jerk_j^2                    (12개 관절 합)
```

2차 차분이 0이라는 것은 **액션이 일정한 속도로 변하고 있다**는 뜻이다.
급가속·급정지만 벌하고, 부드러운 변화는 통과시킨다.

## 채울 곳

`starter/rewards.py` 의 `TODO(reward-smoothness)` — `action_smoothness_l2.__call__`.

**함정이 둘 있다.**

1. IsaacLab 의 `action_manager` 는 `action`(t)과 `prev_action`(t−1)**만** 준다.
   t−2 는 이 클래스가 `self.prev_prev_action` 으로 직접 들고 있어야 한다.
2. 그냥 대입하면 같은 텐서를 가리키게 된다. 왜 `.clone()` 이 필요한지 생각해 본다.

## 검증

```bash
python check.py
```

| # | 통과 기준 |
|:---:|---|
| 1 | 반환이 `(num_envs,)` — env 당 스칼라 하나 |
| 2 | 액션이 계속 0 이면 저크 0 |
| 3 | **선형 램프면 저크 0** — 등속 변화는 벌하지 않는다 |
| 4 | `a=(0,0,1)` → `12` (관절 12개 × 1²) |
| 5 | **t−2 버퍼 갱신됨** — 안 하면 `a=(0,1,2)` 에서 48 이 나온다 |
| 6 | `prev_prev_action` 이 별칭이 아니다 (`.clone()`) |
| 7 | `reset()` 이 버퍼를 0 으로 되돌린다 |

5번과 6번이 이 실습의 핵심이다. 계산식만 맞추면 1~4는 통과하지만
**상태 관리를 틀리면 학습 중에 조용히 잘못된 보상이 흐른다.**

## 왜 상태를 직접 들고 있어야 하는가

IsaacLab 의 `ManagerTermBase` 는 이런 경우를 위해 있다. 보상 항이 상태를 가지면
`reset(env_ids)` 도 반드시 구현해야 한다 — 에피소드가 끝난 env 의 버퍼를 비우지 않으면
**이전 에피소드의 마지막 액션이 새 에피소드의 t−2 로 새어 들어간다.**

Direct 쪽은 이걸 `dreamwaq_env.py` 안에서 직접 배열로 관리한다. 같은 문제를
두 API 가 어떻게 다르게 푸는지가 Stage 2의 관전 포인트다.
